# ADR-0003: Tool and Workshop Packaging Convention

## Status

Accepted

## Context

Toolio needs a standard way to package, describe, and discover tools and workshops. Without a manifest schema, there is no machine-readable metadata for programmatic discovery, no consistent way to validate contributions, and no taxonomy for classifying content. The conventions established here become the primary interface between tool authors and the discovery mechanism (registry).

Key questions resolved:
- Which fields in `tool.json` are required vs. optional
- Whether `platforms` is required or optional (decision: optional, defaults to `["generic"]`)
- Whether tool dependencies are supported in v1 (decision: no, keep flat)
- The exact slug pattern regex
- JSON Schema Draft version
- Workshop manifest structure and step file format
- Type taxonomy for tools
- Difficulty taxonomy for workshops
- Schema validation toolchain choice (`check-jsonschema`)

## Decision

### Tool Manifest (`tool.json`)

Every tool directory must contain a `tool.json` file conforming to JSON Schema Draft 2020-12.

**Required fields:**

| Field | Type | Description |
|-------|------|-------------|
| `name` | string | Slug matching `^[a-z0-9][a-z0-9-]*$` |
| `displayName` | string | Human-readable name |
| `version` | string | SemVer (e.g., `"1.0.0"`) |
| `description` | string | One-line summary |
| `author` | string | Author name or handle |
| `license` | string | SPDX identifier |
| `type` | string | One of the type taxonomy values |
| `tags` | array of strings | Discovery keywords |
| `entrypoint` | string | Relative path to primary file |

**Optional fields:**

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `platforms` | array of strings | `["generic"]` | Target platforms |
| `repository` | string | — | Source repository URL |

**Type taxonomy (enum):**

- `agent-instruction` — Agent prompt/instruction files
- `script` — Executable scripts (bash, python, etc.)
- `config` — Configuration files/templates
- `skill` — APS-compliant skills with SKILL.md entrypoint
- `extension` — IDE or platform extensions

### Workshop Manifest (`workshop.json`)

Every workshop directory must contain a `workshop.json` file conforming to JSON Schema Draft 2020-12.

**Required fields:**

| Field | Type | Description |
|-------|------|-------------|
| `name` | string | Slug matching `^[a-z0-9][a-z0-9-]*$` |
| `displayName` | string | Human-readable name |
| `version` | string | SemVer |
| `description` | string | One-line summary |
| `author` | string | Author name or handle |
| `license` | string | SPDX identifier |
| `difficulty` | string | One of: `beginner`, `intermediate`, `advanced` |
| `estimatedDuration` | string | Human-readable duration (e.g., `"2h"`, `"30m"`) |
| `prerequisites` | array of strings | Required knowledge/tools |
| `objectives` | array of strings | Learning objectives |

### Workshop Step Files

- Workshops must contain a `steps/` subdirectory
- Step files use numbered naming: `01-introduction.md`, `02-exercise.md`, etc.
- Step files are pure Markdown (no required frontmatter in v1)
- At least one step file is required

### Slug Naming Convention

All tool and workshop directory names (slugs) must match: `^[a-z0-9][a-z0-9-]*$`

- Lowercase alphanumeric and hyphens only
- Must start with a letter or digit (not a hyphen)
- No uppercase, underscores, dots, or spaces

### Registry Structure (`tools/registry.json`)

The registry is a derived file generated by `scripts/rebuild-registry.sh`. It is never hand-edited.

```json
{
  "$schema": "../schemas/registry.schema.json",
  "generatedAt": "2024-01-01T00:00:00Z",
  "tools": [
    {
      "name": "example-tool",
      "displayName": "Example Tool",
      "version": "1.0.0",
      "description": "...",
      "type": "agent-instruction",
      "path": "tools/example-tool"
    }
  ],
  "workshops": [
    {
      "name": "example-workshop",
      "displayName": "Example Workshop",
      "version": "1.0.0",
      "description": "...",
      "difficulty": "beginner",
      "path": "workshops/example-workshop"
    }
  ]
}
```

### Registry Rebuild Mechanism

- Script: `scripts/rebuild-registry.sh` (bash + jq)
- Scans `tools/*/tool.json` and `workshops/*/workshop.json`
- Validates slug pattern before including in registry
- Uses `realpath` + prefix check to prevent path traversal
- Fails with clear error if `jq` is not installed
- Produces empty arrays (not errors) for empty directories
- Skips directories without valid manifests (emits warning to stderr)
- Ignores hidden directories

### Schema Validation Toolchain

Use `check-jsonschema` (Python) for JSON Schema validation:
- Native CLI with zero config
- First-class JSON Schema Draft 2020-12 support
- Available in devcontainer via `uv` / pip
- Command: `check-jsonschema --schemafile schemas/tool.schema.json tools/*/tool.json`

## Alternatives

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| YAML manifests (tool.yaml) | More human-readable | Requires YAML parser; harder to validate with JSON Schema | JSON Schema tooling is more mature |
| Package.json style (reuse npm schema) | Familiar to JS developers | Too many irrelevant fields; wrong semantics for content repo | Over-engineered for non-code packages |
| SKILL.md frontmatter (YAML in Markdown) | Already exists in APS skill | Not machine-parseable without frontmatter parser; harder for CI | JSON is universally parseable |
| ajv-cli for validation | Widely known in JS community | Requires config file; Draft 2020-12 support less native | check-jsonschema is simpler for CLI use |
| Flat tools (no subdirectories) | Simpler file tree | No room for README, assets, or multi-file tools | Insufficient structure for real tools |

## Consequences

### Positive
- Every tool and workshop is self-describing via its manifest
- Machine-readable registry enables programmatic discovery and search
- JSON Schema validation catches errors before merge
- Type taxonomy enables catalogue organization and filtering
- Slug pattern prevents filesystem issues and URL-unsafe names

### Negative
- Contributors must create a `tool.json` / `workshop.json` for every contribution (overhead for simple tools)
- Adding new types or difficulty levels requires updating the schema
- `check-jsonschema` adds a Python dependency to CI

### Neutral
- The registry rebuild is a simple bash+jq script with no complex dependencies
- Workshop step files remain pure Markdown, allowing future frontmatter addition without breaking changes
