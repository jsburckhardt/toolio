Module 4 · Core

Brownfield onboarding

⏱ 25 min Pair: swap roles from M3 Requires: a real repo you didn’t write today

Goal: greenfield is easy. Brownfield is the test. You can’t paste an empty project/architecture/ on top of a codebase that already has implicit decisions baked into it.

What you’ll learn

  • How to surface the ADRs a brownfield repo is silently enforcing.
  • The difference between a real decision and a happy accident.
  • Why “onboarding” is itself an RPIV workitem.

Concept

Every real codebase is making architectural decisions. Most of them are unwritten. The choice of test framework, the directory layout, the way errors propagate, what gets logged at what level — all decisions, all implicit, all enforced by code review or sheer habit.

If you drop an agent into that repo and ask it to add a feature, the agent will invent a different framework, a different layout, a different error style. Not because it’s wrong — because there’s nothing telling it what right looks like.

Brownfield onboarding is the bridge from “code that exists” to “code an agent can extend without drift”. Without this bridge, RPIV on brownfield is theatre.

Exercise 4.1

Pick a real brownfield

Pick any real repo you have nearby:

  • Your own side project from two years ago.
  • An open-source repo you know well.
  • That work repo nobody’s touched in a year.

Do not add the soft-factory structure yet. Don’t create project/. Don’t create AGENTS.md. Leave it untouched.

Exercise 4.2

Run an onboarding pass

Open a workitem in that repo: WI-0001-repository-understanding. The agent’s job is not to write code. It’s to:

  1. Read every directory at depth 1, summarise what it does in one sentence.
  2. Read the test layout and reverse-engineer the test conventions (framework, naming, location).
  3. Read the CI config and list everything it enforces (linters, type checks, secret scans, required reviewers).
  4. Surface the implicit ADRs — decisions the code is making that aren’t written down anywhere.

The output is a draft project/architecture/ADR/ with ADRs inferred from the code, plus a core-components/ listing the major modules.

What you should see

Something like:

ADR-DRAFT-0001 — Python 3.11+ as runtime
  Evidence: pyproject.toml requires-python; CI matrix.

ADR-DRAFT-0002 — pytest as test framework
  Evidence: tests/conftest.py exists; tests/test_*.py pattern.

ADR-DRAFT-0003 — All routes are async
  Evidence: 14/14 route handlers in src/api/*.py use async def.

ADR-DRAFT-0004 — Errors map to JSON envelopes
  Evidence: src/errors.py defines envelope(); used in 12 places.
Exercise 4.3

Negotiate

Look at the inferred ADRs as a pair. Argue. For each one, ask:

  • Is this a real decision someone made on purpose?
  • Or is it an accident nobody intended — whoever wrote the first endpoint picked async, and everyone copy-pasted?
  • Or is it a partial truth — some routes are async, some aren’t, and you should pick one and migrate?

Promote the real decisions to ADR-0001, ADR-0002, etc. Delete the accidents. Flag the partial truths as work to do.

Debrief

  • How many drafts did you promote? How many did you delete?
  • How many promoted ADRs would have been useful for the last bug you fixed in that repo?
  • Where would a new joiner have learnt these decisions today, without the ADRs?

Takeaway

Onboarding is the bridge from “code that exists” to “code that an agent can extend without drift”. Without this bridge, RPIV on brownfield is theatre.

You don’t need to onboard the whole repo on day one. You need to onboard the slice you’re about to change. The rest can wait.
