Module 3 · Core

Shared architecture

⏱ 20 min Pair: swap roles from M2 Builds on the issue you closed in M2

Goal: the lego brick everyone reads from. ADRs and core-components live outside any single workitem.

What you’ll learn

  • The difference between a workitem decision and an architectural decision.
  • The four-section ADR template (Context / Decision / Consequences / Status).
  • How to make Research read your ADRs automatically next time.

Concept

In Module 2 you built one endpoint, fully RPIV. If you build a second endpoint tomorrow, you’ll write a fresh research brief and a fresh plan — and you’ll re-discover the same decisions you made for endpoint one.

Architecture is the decisions that outlive any single workitem. They don’t belong in project/issues/42/plan.md — they belong somewhere global, where future Research stages will find them.

In the soft-factory repo, that’s project/architecture/ADR/ and project/architecture/core-components/, with DECISION-LOG.md as the index.

Exercise 3.1

Promote a decision to an ADR

Look at your plan.md from Module 2. You almost certainly made a decision that wasn’t load-bearing for that workitem but will matter for the next one. Examples:

  • “Every endpoint returns {ok: bool}”
  • “Use pydantic not marshmallow”
  • “Log at INFO not DEBUG by default”
  • “All filesystem paths resolved through realpath with prefix check”

Promote it to an ADR:

$EDITOR project/architecture/ADR/ADR-0001-response-envelope.md

Use this template — four sections, no more, no less:

# ADR-0001 — <decision>

## Context
<why this came up>

## Decision
<one paragraph, in present tense>

## Consequences
<what becomes easier; what becomes harder>

## Status
Accepted — <date>

Then index it in the decision log:

$EDITOR project/architecture/DECISION-LOG.md
# Append one line — ID, title, status, date.

What you should see

A four-section file under ADR/. A one-line entry appended to DECISION-LOG.md. Total writing time: 5–7 minutes if you’re disciplined.

Exercise 3.2

Make Research read it

Re-run the Research stage for a new issue. The brief MUST now list ADR-0001 under “Decisions discovered” if it’s relevant.

If the agent misses it, the Research stage isn’t strong enough yet. Add an explicit instruction to AGENTS.md:

# In AGENTS.md, in the Research stage section:
Research MUST grep project/architecture/ADR/ and project/architecture/core-components/
before producing the brief, and list every applicable ADR by ID.

Re-run Research. The brief should now find your ADR automatically.

Debrief

  • Which of your Module 2 plan steps would have been shorter if ADR-0001 had existed earlier?
  • If you have two ADRs that contradict each other, what does the brief say?
  • Who is responsible for keeping DECISION-LOG.md in sync — the trainee, the agent, or CI?

Takeaway

Architecture artifacts live outside any workitem. Research reads them. Plan respects them. Implement complies with them. Verify checks compliance.

This is the difference between an agent that gets better over time and one that keeps re-inventing the wheel.
