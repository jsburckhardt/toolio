Module 7 · Stretch

Parallel agents

⏱ 20 min Stretch — skip in 90-min slot Requires: a feature with 3+ independent stories

Goal: decompose a feature into multiple workitems that don’t step on each other.

What you’ll learn

  • git worktree as the parallelism primitive.
  • The difference between a rendezvous point (must coordinate) and a fan-out point (parallel-safe).
  • How shared architecture (Module 3) is what makes parallelism survive merge.

Concept

One agent on one workitem is easy. Three agents on three workitems against the same repo is where the harness earns its keep. Each agent must respect the same ADRs, the same core-components, the same conventions — otherwise they’ll each invent locally-plausible changes that collide globally.

Surfaces in your repo fall into two categories:

  • Rendezvous points — only one workitem touches them at a time (the ADR directory, shared schemas, top-level config). Need coordination.
  • Fan-out points — many workitems touch them safely in parallel (separate route files, separate test files, separate modules). Parallel-safe.
Exercise 7.1

Decompose

Take a feature with at least 3 independent stories. Open 3 GitHub issues:

gh issue create --title "WI-43: add /users endpoint"
gh issue create --title "WI-44: add /orders endpoint"
gh issue create --title "WI-45: add /products endpoint"

Use git worktree to set up three working copies, one per issue:

git worktree add ../soft-factory-WI-43 -b feature/wi-43
git worktree add ../soft-factory-WI-44 -b feature/wi-44
git worktree add ../soft-factory-WI-45 -b feature/wi-45

Each worktree is a full checkout of the repo on its own branch, sharing the same .git/ common dir.

Exercise 7.2

Run RPIV in parallel

Open three terminals (or three agent sessions). Run the full RPIV loop against each worktree simultaneously.

The constraint

All three workitems MUST respect the same ADRs. None of them can silently change project/architecture/.

If a workitem needs a new ADR, that’s a separate workitem with its own issue. Architectural change is never a side effect.

What you should see

Three branches finish independently. Each has its own project/issues/<N>/ folder. Each consumed the same ADRs. None of them touched project/architecture/.

Exercise 7.3

Where do they collide?

When the three branches hit main, where do conflicts land? Walk through it as a pair:

  • File-level conflicts: two branches modified the same line of the same file. Rare if you decomposed well.
  • Schema-level conflicts: two branches added competing columns or fields. Often caught by tests, sometimes silent.
  • ADR-level conflicts: two branches made incompatible assumptions about an ADR (e.g., both added a route that conflicts on URL pattern). The hardest to spot; only catches in integration.

Update AGENTS.md to declare which surfaces are rendezvous-points and which are fan-out-points:

## Rendezvous points (single-writer at a time)
- project/architecture/
- schemas/
- top-level config (pyproject.toml, package.json)

## Fan-out points (parallel-safe)
- src/routes/ (one file per endpoint)
- tests/ (co-located with source)
- project/issues/<N>/ (per-WI; never overlaps)

Debrief

  • How many of your three workitems touched a rendezvous point you didn’t expect?
  • What pattern in your code makes a surface accidentally a rendezvous point? (Hint: shared mutable state, global registries, central config.)
  • If you ran 10 worktrees in parallel instead of 3, which surface breaks first?

Takeaway

The frontier isn’t whether the flow works. The flow is fine. The frontier is how far you can scale parallelism before the harness needs to grow.

Every rendezvous point you discover is a hint about where the next harness component belongs.
