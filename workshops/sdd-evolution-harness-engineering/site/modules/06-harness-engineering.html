Module 6 · Stretch · The naming module

Harness engineering

⏱ 30 min Stretch — skip in 90-min slot Pre-read: Böckeler, Harness engineering for coding agent users

Goal: name what you’ve been building. agent = model + harness.

What you’ll learn

  • The vocabulary: guide, sensor, computational, inferential.
  • The 2×2 that organises every harness component you’ve built so far.
  • The steering loop: when an issue recurs, upgrade the harness, not the prompt.

Concept

Read this before the exercise: Birgitta Böckeler — Harness engineering for coding agent users (martinfowler.com, April 2026). Skim section 2 (“Guides and sensors”).

The frame:

  • An agent is a model (the LLM) plus a harness (everything you’ve built around it).
  • Guides are feedforward: they tell the agent what to do, before it acts.
  • Sensors are feedback: they tell the agent (or you) what just happened, after it acts.
  • Both come in two flavours:
    • Computational: deterministic, fast, code-defined.
    • Inferential: LLM-as-judge, slow, prompt-defined.

Exercise 6.1

Map your existing pieces

Take your repo as it stands at the end of Module 5. List every guide and every sensor you have. Place each in the 2×2 above.

Worked example for a small Python repo:

ItemQuadrant
pyproject.toml dependency pinsComputational guide
AGENTS.md “MUST use async”Inferential guide
pre-commit running ruffComputational sensor
CodeRabbit on PRsInferential sensor

Where are the empty quadrants? Those are the gaps.

Exercise 6.2

Fill one empty quadrant

Pick one empty quadrant. Add a minimum-viable thing:

  • Empty computational sensor → add one pre-commit hook (ruff, eslint, or a custom forbid-print-in-production.sh).
  • Empty inferential sensor → write a 20-line Skill / Claude prompt that reviews PR diffs and posts a comment if it spots an ADR violation.
  • Empty computational guide → add a cookiecutter or generator that produces a new module pre-filled with the right structure.
  • Empty inferential guide → expand AGENTS.md with a “MUST NOT” section listing the three things the agent keeps getting wrong on this repo.

What you should see

One quadrant lights up. Future workitems benefit from it. The thing you added is tiny — that’s the point. You don’t need to fill all four cells today.

Exercise 6.3

The steering loop

The harness wins when you stop firefighting prompts.

The rule

When the same issue recurs, don’t patch the prompt for that one workitem. Upgrade the harness so the issue can’t happen again.

Worked example:

Recurring problemWrong fixRight fix
Agent keeps hardcoding localhost Tell the agent in chat “don’t hardcode” Pre-commit hook fails on localhost in production code (computational sensor)
Agent invents a new test runner Re-paste the test runner choice every prompt Add an ADR + an instruction in AGENTS.md (inferential guide)
Agent skips writing verify.md Remind it in chat CI gate that blocks PR if verify.md is missing (computational sensor)

Debrief

  • What’s the most recent prompt you wrote that you would not have needed if your harness were one notch better?
  • Which quadrant would that improvement live in?

Takeaway

Feed-forward only = rules with no verdict. Feedback only = same mistake every time. You need both, and you need to keep upgrading both.

That’s harness engineering. That’s the job.
