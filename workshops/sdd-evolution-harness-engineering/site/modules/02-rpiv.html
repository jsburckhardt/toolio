Module 2 · Core

RPIV crystallises

⏱ 35 min Pair: swap roles from M1 The biggest module — pace yourselves

Goal: add Research in front of Plan, and Verify after Implement. That’s the full RPIV loop.

What you’ll learn

  • Why Plan/Implement breaks the moment you do it twice.
  • The four stages of RPIV and the artifact each one produces.
  • How to make every step in plan.md cite its evidence in research.md.
  • Why verify.md is a ledger, not a test report.

Why Research

Plan/Implement worked in Module 1 until you tried to be consistent across iterations. Endpoint 1 had observability. Endpoint 2 didn’t. Neither one matched the existing patterns in the repo. The plans were locally fine and globally incoherent.

Research forces the agent to find what already exists before it plans something new. It’s a context-gathering pass with a written output. No code. No decisions. Just what’s here, what decisions apply, what’s missing, what could break.

The full loop

Research → research.md (context, applicable decisions, gaps, risks) ↓ Plan → plan.md (what / where / why; every step cites research) ↓ Implement → code + tests (compliant with the plan) ↓ Verify → verify.md (acceptance criteria, evidence, PR link)

Each stage produces a file. The next stage reads the previous file. Nothing else.

Exercise 2.1

Research stage

Create a fresh issue:

gh issue create --title "Add /healthz endpoint"

The agent’s first job for this new issue is a research brief, not code. Save it as project/issues/<N>/research.md:

# Research — WI-<N>

## Context discovered
<what already exists in this repo that’s relevant —
 file paths, existing endpoints, conventions>

## Decisions discovered
<ADRs that apply — list by ID; if none apply, say “none applicable”>

## Gaps
<what’s missing that the plan will need to invent or escalate>

## Risks
<concrete things that could break if we get this wrong>

Ask your agent to produce this brief by searching the repo. Read it carefully. Reject it if it’s generic. A research brief that says “the codebase uses Python” is worthless — you need file paths, function names, existing endpoint conventions.

Common failure mode

Agents love to produce research briefs that sound thorough but cite nothing. If your brief has no file paths or line numbers, it’s a synopsis, not a brief. Send it back.

Exercise 2.2

Plan, anchored to research

Now write plan.md using the same template as Module 1, but with one new rule:

The anchoring rule

Every step in plan.md MUST cite the line in research.md that justifies it.

If a step has no justification, you have two choices:

  1. Move it to “What I won’t do” (you’re inventing scope — back out).
  2. Go back to Research and expand the brief.

Debrief

  • How many of your plan steps had to be reworded because the research couldn’t back them?
  • Did Research force a decision you would otherwise have made silently?
Exercise 2.3

Implement

Run implement. Code and tests land in the repo. Nothing surprising should happen — every choice the agent makes is traceable back to a plan step, which is traceable back to a research finding.

If you’re surprised, the surprise is the lesson. Find which plan step left room for invention and tighten it.

Exercise 2.4

Verify

Create project/issues/<N>/verify.md. This is not a test report. It’s a verification ledger:

# Verify — WI-<N>

## Acceptance criteria
- [ ] <criterion 1 from the issue>
- [ ] <criterion 2>

## Evidence
| Criterion | Evidence                                                    |
|-----------|-------------------------------------------------------------|
| 1         | tests/test_health.py::test_returns_200 passes               |
| 2         | manual check: curl localhost:8000/healthz → {"ok": true}  |

## ADRs touched
<list any ADR or core-component this WI depends on or modified>

## PR
<URL once opened>

Open the PR. Link the issue. Tick the boxes. Done.

What you should see in review

Your reviewer reads four files in order — research.md, plan.md, the diff, verify.md — and can answer “why does this code exist?” without asking you a single question.

Takeaway

The issue’s acceptance criteria is the contract. Verify closes against the contract, not against “looks good to me”. Research provides the evidence. Plan provides the reasoning. Implement provides the artifact. Verify proves the contract held.

This is RPIV. The rest of the workshop is about how to scale it — across decisions (M3), across codebases (M4), across upstream agents (M5), across teams (M6), and across parallel work (M7).
